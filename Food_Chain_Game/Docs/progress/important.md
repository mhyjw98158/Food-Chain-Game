# 중요 — 나중에 반드시 처리할 것

## 음성 채널 입장 권한 발급 (엿듣기 방지)

작성: 2026-10-12 / 상태: **미구현(보류)** — Steam 출시 준비 단계에서 진행하기로 결정(2026-10-30)

### 지금의 문제
- 음성 채널 이름은 `lobby_방코드`, `alive_방코드`, `dead_방코드`로, 방 코드만 알면 누구나 만들 수 있다.
- 현재는 Unity 인증으로 로그인한 플레이어라면 **어떤 채널이든 들어갈 수 있다.** 채널에 들어갈 자격을 검사하는 곳이 없다.
- "누가 들리는지"(거리, 벽, 생존/유령)는 **듣는 쪽 클라이언트가 음량을 0으로 낮추는 방식**이다(`InGameVoiceProximity`). 소리 자체는 전부 받고 있다.

그래서 변조된 클라이언트는 다음이 가능하다.
1. 생존자인 채로 `dead_` 채널에 들어가 유령들의 대화를 듣는다(누가 죽었는지, 범인이 누구인지).
2. 거리·벽 제한을 끄고 생존자 전원의 대화를 듣는다.
3. 죽은 뒤에도 `alive_` 채널에 말한다.
4. 방 코드만 아는 외부인이 게임에 접속하지 않고 음성만 듣는다.

### 해결 방향
Vivox는 로그인·채널 입장 때마다 **입장 토큰**을 요구할 수 있다. 이 토큰을 클라이언트가 아니라 **우리 서버가 서명해서 발급**하면, 서버가 허락한 채널에만 들어갈 수 있다.

1. 토큰 서명 키는 서버에만 둔다(클라이언트·저장소에 넣지 않는다).
2. 클라이언트는 채널에 들어가기 전에 서버에 "이 채널 토큰을 달라"고 요청한다.
3. 서버는 요청한 플레이어가 그 방의 구성원인지, 그 채널에 들어갈 상태인지(생존자 → `alive_`, 유령 → `dead_` + `alive_` 듣기) 확인하고 토큰을 준다. 토큰은 짧게(수십 초) 만료시킨다.
4. Unity 쪽은 토큰 발급기(`IVivoxTokenProvider`)를 구현해 `VivoxService`에 등록한다. 등록 시점과 정확한 사용법은 설치된 SDK(16.11.0) 문서로 확인 필요.

### 이 프로젝트에서 따로 풀어야 할 점
- **게임 서버가 플레이어 PC(방장)다.** 방장에게 서명 키를 줄 수 없으므로 토큰은 Node 방 코드 서버(`Server/`)가 발급해야 한다.
- Node 서버는 지금 "누가 살아 있는지"를 모른다. 방장이 생존/사망 상태를 Node 서버에 알려야 하는데, **방장 자신이 변조된 클라이언트일 수 있다.** 방장까지 막으려면 전용 서버가 필요하다(접속 구조 결정과 함께 정해야 함).
- 토큰으로 막을 수 있는 것은 **채널 입장**까지다. 같은 `alive_` 채널 안에서 거리·벽을 무시하고 듣는 것(위 2번)은 토큰으로 막지 못한다. 이것까지 막으려면 가까운 사람끼리만 같은 채널에 두거나, Vivox의 위치 기반 채널을 서버가 정한 위치로 쓰는 방식이 필요하다.
- 죽은 사람을 `alive_` 채널에서 말하지 못하게 하려면 서버가 강제로 음소거/퇴장시키는 토큰(권한)도 필요하다.

### 시작 전에 확인할 것 (2026-10-30 조사)
- **Vivox 자격 정보:** Unity 대시보드의 Issuer와 서명 키가 필요하다. 키는 저장소에 넣지 않고 Node 서버 환경 변수로만 둔다.
- **우회 경로:** 설치된 SDK에는 개발자용 `IVivoxTokenProvider`(`VivoxService.Instance.SetTokenProvider`) 외에 Unity 로그인 기반 내부 토큰 경로(`InternalTokenProvider`)가 따로 있다. 변조 클라이언트가 이 경로로 토큰을 받을 수 있는지, 대시보드에서 끌 수 있는지를 **먼저 확인한다.** 끌 수 없다면 서버 발급 토큰을 넣어도 입장 제한이 되지 않는다.
- **서버 의존:** 토큰을 Node 서버가 발급하면 그 서버가 꺼졌을 때 새 채널 입장이 막혀 음성이 끊긴다. 지금처럼 개인 PC + Cloudflare Tunnel로 운영하는 동안에는 위험이 크다. 안정적인 서버가 생긴 뒤에 진행한다.
- **플레이어 확인:** Node 서버는 요청자가 누구인지 모른다. 방장이 플레이어별 임시 값을 발급해 Node 서버에 등록하고, 클라이언트가 그 값으로 토큰을 요청하는 구조가 필요하다.

### 우선순위 제안
1. `dead_` 채널 입장 제한(유령 대화 엿듣기) — 게임 결과에 가장 큰 영향
2. 방 구성원이 아닌 사람의 입장 차단
3. 거리·벽 무시 듣기 방지 — 구조 변경이 커서 마지막

## 클라이언트에 전달되는 정보 (2026-10-30 점검)

동기화 변수, 전체 RPC, 네트워크 메시지, 컴포넌트 Sync Mode를 전수 조사했다. 역할(`animalType`, `isPredator`, 미션, 위장, 굶주림 등)은 서버와 본인만 가지며 다른 클라이언트로 가지 않는다. 아래는 역할은 아니지만 **변조된 클라이언트가 읽을 수 있는** 남은 정보다. 일반 클라이언트 화면에는 드러나지 않는다.

| 정보 | 현재 | 영향 |
|---|---|---|
| 전원의 위치 | 시야와 상관없이 모두 전송(Interest Management 없음) | 맵핵 가능. 어두운 곳, 벽 너머의 플레이어 위치를 알 수 있다 |
| 생사 | `isAlive`가 SyncVar라 사망 즉시 전원에게 전송 | 시체를 발견하기 전에 누가 언제 죽었는지 알 수 있다 |
| 시체 위치 | 전원에게 스폰 | 시야 밖의 시체 위치를 알 수 있다 |

### 고치려면
시야 판정은 지금 클라이언트에서 한다(`FOVMaskController2D`). 위치를 숨기려면 서버가 플레이어별로 "이 사람에게 보여도 되는가"를 벽까지 계산하는 Interest Management가 필요하다. 다만 근접 음성(`InGameVoiceProximity`)과 시야 공유(얼룩말·타조)가 다른 플레이어의 위치를 쓰므로 함께 바꿔야 하고, 플레이어 수만큼 계산이 늘어 방장 PC 부담도 커진다. 유령을 생존자에게 보내지 않으려면 같은 장치가 필요하다.

방장은 서버를 겸하므로 모든 정보를 가진다(전용 서버 없이는 막을 수 없다).
